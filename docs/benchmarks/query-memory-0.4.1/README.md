# 0.4.1 后台刷新与更新分配验收

日期：2026-10-26。用户报告空闲时查询时间跳动、内存7G。以下记录不代表达到Everything内存或亿级性能目标。

## 真实运行进程的定位

用户0.4.0前台进程工作集曾约8298MiB、私有9805MiB，后台采集进程仅约128MiB；同期Everything主进程约3091MiB工作集、3197MiB私有内存。无暂停的10秒System.Runtime采样：分配中位约48MiB/秒，范围21–426MiB/秒；GC暂停峰值约0.4秒/秒，GC提交约10–11GB。完整原始数据见runtime-0.4.0.csv，不能把峰值当中位数。

原因包括：后台索引变更无条件取消并重新执行用户查询、重置页码并覆盖计时；已有目录变化会为整卷生成等值路径字符串；微小增量名称arena先分配2MiB再裁短；检查点读取和清理反复生成无需保留的完整目录文本。

## 固定真实输入的Windows对照

独立诊断进程分别载入同一套停止写入的9卷V3快照、检查点和WAL，共34,409,868行，之后仅在内存中新增3个独立目录。没有改生产文件、强制GC用户进程、修改数据库或设置GC策略。新旧Core DLL哈希与版本记录在结果JSON中。一个初版诊断构建因引用缓存误载旧DLL，已排除；最终新版使用独立工程且校验Core=0.4.1.0和DLL SHA256。

## 小规模可重复回归与正确性

同一10万目录合成输入，新增独立目录首次分配约5.8KB（旧版约46.5MB），普通文件新增约4.4KB（旧版约2.1MB）。叶目录改名稳态分配约909KB（旧版约49.5MB），保留目录引用表、隐藏位图和排序修正所需成本。

叶改名5次预热、30次采样、3轮独立Linux进程的中位数：旧版32.73/33.01/33.70ms；正确的祖先身份筛选7.18/7.01/6.69ms。曾尝试仅按旧路径前缀过滤，但两遍扫描和硬链接即时路径可能形成混合历史名称；review复现了漏更新和删除残留，已改为旧图祖先身份判断及固定4096项复用缓存。未以更快但错误的前缀方案交付。

Windows、Linux各151项测试通过；独立review额外2500批随机目录移动、8种排序方向与旧实现一致，混合路径、代际、环检测、缓存换出、取消后复用通过。WPF自检验证用户计时/第三页/选中项/真实DataGrid滚动保留、实际新增删除、元数据更新与末页删除夹取。新版本兼容0.4.0的数据库和检查点，不因格式升级重扫。

## 实际Windows前台恢复

最终Windows前台恢复9卷34,414,502对象，ScansStarted为空；新增、改名、删除和停机补读通过。诊断入口未强制GC：工作集5,711,491,072B（5.319GiB），私有5,746,700,288B（5.352GiB），托管占用5,460,181,728B。此时前台已经加载全部卷，仍未达到Everything的内存水平。
