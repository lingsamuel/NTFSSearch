# 0.4.0 功能与恢复验收

日期：2026-10-26。以下是实际Windows NTFS功能验证，不是亿级性能达标报告。

## 结果

- Windows与Linux各132项测试通过。Windows实际覆盖head短暂锁、200事务与8个读者并发追加/压缩、跨压缩旧句柄读取；这些Windows语义问题均先复现失败，再修复验证。
- 9卷V3基线已完整发布。两次重启验收均恢复全部9卷，`ScansStarted=[]`，无任何全量扫描任务；报告总数分别34,409,358和34,409,867，期间对象仍在变化。
- 普通前台、独立管理员采集、WAL和查询发布整条链路验证新增/改名/删除。先让旧进程观察删除，再关闭进程并重新创建文件，重启确认`OfflineRecovered=true`。
- 独立实际硬链接案例验证两链名、新增、目录移动、删除一条硬链接、保存检查点、停机变化回放与递归删除。各阶段计数5/4/4/0，全卷重扫次数0。
- 默认数据为exe旁`Data`；迁移、目标优先、源保留、取消、跨进程锁、坏清单和只读发布错误均有回归覆盖。旧V1/V2升级需要一次重建；正常V3启动只恢复检查点和尾部日志。

上述逐卷查询在持续变动的系统上顺序执行，不是同一时刻的文件系统快照。Everything全局34,402,750；工具第二次报告34,409,867。E/F/G/I/J/K六卷均比Everything多7项；H卷还排除了工具自身Data（SDK当时计207项）。C/D仍有约7千/数百的差额，不能将总量接近宣称为逐文件完全一致。

额外只读核查C卷7,690,405条可见路径：完全相同路径、忽略大小写路径、完整FRN/父ID/名称组合的重复项均为0；WAL涉及3,103个FRN，未发现删除后残留、旧代际残留或已删除父链仍可见。该验证排除这些具体错误，不代替SDK差额的文件级解释。额外点查了3个Office文件：新版的原Download链和新增Office根目录链均实际存在；SDK收录原链（各1项），但根目录链均为0项。结果见hardlink-sdk-samples.json。至少这3项是SDK尚未收录的真实硬链接，不能按较少总数反向删除。整段路径再次加引号查询：Office16前缀新版9,498/SDK8,220，WindowsApps前缀新版103,861/SDK98,404；两个不相交前缀合计贡献6,735项差额，覆盖C卷差额的大部分，但尚未逐文件解释所有剩余项。

Everything 1.4的硬链接增量有其限制，官方说明不能自动检测新增/变化/删除的所有硬链接，因此现有SDK库也不能直接当作实时文件系统真值；本次没有强制重建或修改其数据库。[官方开发者说明](https://voidtools.com/forum/viewtopic.php?t=17862)

## 性能边界

本轮没有完成3500万/1亿对象的同机搜索、排序、内存及大量变化尾延迟对标。不能用这些正确性、恢复与数量记录宣布达到Everything的即时体验。初次基线与目录变动的性能仍需继续验收。
