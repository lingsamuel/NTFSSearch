# Windows NTFS 文件搜索工具设计

日期：2026-10-26。

状态：用户已确认功能范围和基本方案，并补充亿级性能要求。用户明确否定未经实测提出的 16 GiB 内存预算和 400 ms 计数延迟。以当前 Everything 的资源占用和即时搜索、排序体验为基准，不得自行放宽标准。

## 目标与范围

- 独立实现 Windows 本机 NTFS 文件和目录搜索，不依赖 Everything 进程或数据库运行。
- 以当前约 3500 万个对象为实际使用基线，以 1 亿个可搜索目录项为容量设计与测试规模。
- 支持名称和完整路径匹配，名称、完整路径、文件大小、修改时间的升序和降序排序。
- 默认空格分隔多个条件，所有条件必须满足；双引号内的空格属于连续匹配文本。
- 优先解决大规模变动后响应停顿、启动恢复失败、运行中无法诊断的卡死。
- 不包含文件内容搜索、远程服务、网络共享、非 NTFS 文件系统、WSL 内部文件系统。
- 本机索引后台服务属于桌面程序组成部分，不开放网络监听端口。
- 首版不计算目录递归大小，不实现完整 Everything 查询语言、模糊匹配或拼音匹配。

## 用户机器与现有基线

2026-10-26 经 WSL 调用 Windows PowerShell 只读检查：

- Windows 11 Pro，系统版本 10.0.26200。
- AMD Ryzen 9 9950X3D，16 核、32 逻辑线程。
- 系统报告可用物理容量约 95.56 GiB，按约 96 GB 配置考虑。
- 6 块 NVMe SSD、3 块 SATA HDD；9 个带盘符的 NTFS 卷。
- 用户报告 Everything 当前约 3500 万个对象，搜索和排序几乎无感。
- 检查时 Everything 主进程工作集约 3.04 GiB、私有内存约 3.12 GiB。这是单次观测，不能推导峰值或所有索引配置。
- 当前运行版本为 Everything 1.4.1.1009。已只读确认开启完整路径匹配、文件大小和修改时间索引，以及名称、路径、大小、修改时间的快速排序；目录大小索引关闭。对标必须使用这些实际配置。

硬件、进程占用等可直接读取的信息由工具自主检查。机器配有 96 GB 内存不代表可以任意扩大常驻占用；资源效率需要对标 Everything，不能用硬件余量解释回退。

## 实现路线与复用边界

已确认的 C#、.NET 10 和 WPF 是基本桌面方案。核心引擎的语言与数据布局以资源效率和基准结果决定；若不能满足对标要求，应调整引擎实现，不得为保留技术栈而降低性能要求。也不能仅凭对象数量断言某种语言一定可行或不可行。

推荐通过 Windows 提供的 MFT 记录枚举接口建立基础索引，使用 USN 日志持续更新。自行解析原始 MFT 的兼容与恢复负担更大；普通目录遍历的首次扫描和补扫成本更高。大小、修改时间及硬链接补全需要独立采集，不能假设 USN 枚举直接提供这些信息。

项目当前为空仓库。优先使用 Windows 系统接口、.NET 内存映射与成熟的集合、压缩位图组件；只有缺少适用组件且测得必要时，才增加专用实现。第三方组件需要检查许可证、Windows 构建、序列化兼容、取消支持和维护状态。

已发现的参考候选：

- CRoaring：候选集交并与计数的组件候选，不等同于完整的文件搜索引擎。
- everyfind：NTFS 枚举与 USN 流程的阅读候选。尚未完成代码审查，不采用其性能宣传作为证据。
- Everything 官方索引文档：确认持久维护排序索引的行为；不假定其内部数据结构已经公开。

## 匹配与排序语义

- 默认忽略大小写，保留原始文件名；同一比较规则用于索引候选筛选和最终精确校验。
- 普通条件默认匹配完整路径，与用户现有 Everything 配置保持一致；提供仅匹配名称的选项。包含反斜杠的条件始终按路径匹配，其他条件遵循当前模式。
- `hello world` 要求两个子串都出现，位置和顺序不限。
- `"hello world"` 要求出现包含一个空格的连续子串。
- `D:\Work report` 在默认模式下要求完整路径同时包含 `D:\Work` 和 `report`；仅名称模式下，第二个条件匹配名称。含空格的路径需要双引号。
- 引号未闭合时，将剩余输入视为正在输入的短语，不阻塞搜索；双引号不作为文件名搜索字符。
- 不把反斜杠作为通用转义符，避免破坏 Windows 路径。
- 排序定义稳定的次级键：完整路径和卷内目录项标识。升降序的规则一致，分页不重不漏。
- 大小指文件逻辑长度；目录大小显示为空。尚未取得的元数据有明确未知状态，未知值始终排在已知值之后。
- 完整路径排序与其显示文本的比较结果一致，不能仅比较末级父目录编号。
- 搜索结果允许文件与目录混合排序，不引入隐式的“文件夹优先”规则。

## 亿级数据布局

- 文件记录采用分段的紧凑结构、列数组或映射布局，不为每个对象分配独立的完整业务对象。
- 名称保存在连续字符串区，目录关系共享；原始 UTF-16 文件名必须无损保留。
- 文件标识包含卷身份及 NTFS 文件引用的代际信息，防止删除后记录编号复用造成串记录。
- 区分文件对象和可搜索目录项，一个硬链接不能覆盖其他链接。基础枚举不足时使用系统硬链接信息接口补全，并在状态中区分完整与未完整索引。
- 查询和 UI 持有目录项 ID 与有限结果页，不复制全部路径字符串，不创建数千万条 UI 行对象。
- 使用分段快照和有界增量，发布新版本时只替换发生变化的部分，不能复制整份亿级索引。
- 内存计量覆盖所有进程、映射驻留页、增量、查询缓存和压缩临时空间；分别报告私有提交与驻留工作集。

## 查询和排序执行

- 名称子串索引与目录关系索引组合筛选候选。字符或 n-gram 候选仅作过滤，最终必须验证完整匹配，不能漏掉短条件或 Unicode 名称。
- n-gram 会增加存储与更新成本，是否采用、采用哪些长度及高频项策略由规模基准决定。
- 路径匹配复用目录关系与目录匹配结果，避免为每个文件重复保存所有父路径片段。
- 名称、路径、大小、修改时间维护可持久化的排序索引。切换排序利用已维护的顺序，不临时对全部记录排序。
- 查询规划根据候选数量选择按排序索引筛选，或对较小候选集使用排序秩。任何方案都必须验证全局顺序。
- 查询绑定一个已发布版本。精确匹配数、分页与排序来自同一版本；未完成计数时明确显示正在统计。首屏与计数可以分项诊断，但最终以用户获得完整搜索结果的实际延迟验收，不能把较慢的计数隐藏在后台来宣称即时搜索。
- 只传输当前显示页，但完整计数和正确的全局顺序属于验收内容。不能用只返回少数命中来宣称完成全量搜索。
- 取消旧查询并合并连续输入，避免过期查询占满线程和缓存。取消检查覆盖候选计算、精确校验、排序和 IPC。
- 目录重命名影响后代路径、路径匹配和路径排序。版本发布须统一这些变化；受影响路径索引更新完成前维持旧一致版本并标明更新中。

## 进程与职责

- WPF 界面：普通权限，处理输入、有限行展示、打开文件和复制路径，不做卷扫描和大集合排序。
- 本机协调服务：负责索引版本、查询调度、进度和持久化策略。使用带访问控制的本机命名管道，不开放 HTTP 接口。
- 磁盘采集工作进程：持有卷句柄，按卷处理枚举、日志和补充元数据。工作进程可以重启，单盘 I/O 卡住不能持有查询所需的全局锁。
- 服务只提供索引和必要操作；打开文件仍使用当前桌面用户权限。
- 结果、消息和请求大小有上限，IPC 不允许客户端指定任意文件访问或系统命令。

## 批量变动与恢复

- 每卷保存卷标识、日志标识、下一读取 USN、提交版本和格式版本。
- 变动与其对应的日志进度在同一可靠提交边界发布；不得先推进进度再持久保存记录。
- 批量合并需要保持同一文件的因果顺序，不得把删除后重建、硬链接变化或重命名配对简化丢失。
- 对事件、内存和磁盘积压设置上限；队列满时暂停消费并从可靠 USN 位置重读，不静默丢事件。
- 若日志已截断、被重建或卷身份变化，标记受影响卷需要重建；其他卷继续工作。
- 初始枚举前记录日志水位，枚举后回放并处理竞态；只有在无日志缺口并完成一致性检查后发布新版本。
- 重建写入新一代索引；保留可用旧代，可靠发布后再回收。重建期间旧结果明确标为可能过期。
- 启动恢复区分文件格式损坏、日志失效、权限不足、卷离线和 I/O 错误，重试有次数和退避上限，不重复载入同一损坏文件。
- 健康检测同时观察工作进程存活、阶段进度与请求延迟；仅有心跳不足以证明任务正常推进。
- 诊断记录阶段耗时、队列深度、卷状态、版本和资源峰值，默认不记录用户的完整搜索内容或文件内容。

## 性能目标与验收

先建立可重复的性能验证，再开发完整桌面产品。此前提出的 6/16 GiB 内存预算及 100/200/400 ms 固定延迟线没有测量依据，已全部撤回，不能继续作为验收门槛。

- 实际基线：用户的约 3500 万对象，Everything 单次观测约 3.04 GiB 工作集、3.12 GiB 私有内存，搜索和排序几乎无感。先测量查询与排序的实际分布，再形成可复现的数值基线。
- 对标条件：同一台机器、同一份可搜索元数据、相同可比索引字段、相同查询和排序、相同冷热状态；分别列出后台负载和更新活动。
- 3500 万验收：在等价功能和索引条件下，搜索、完整计数、排序响应与常驻资源占用均需不劣于 Everything 的可复现基线。小于测量噪声的差异需多轮验证，不能挑选单次有利结果。
- 亿级验收：从首版开始实测 1 亿目录项，维持即时搜索和排序的体验，并在双方可加载相同测试数据时直接对标 Everything。没有该规模的可比测量时，只能报告容量测试和实测指标，不能宣称已经对标通过。
- 资源计量：报告各组件合计占用和每目录项增量成本，索引字段增加的成本单独列账；不能由对象数量简单线性推导一个较宽松的预算，再把它当作已经达标。
- 体验计量：主要验收从输入或排序操作到正确有序结果与精确计数均可用的延迟，首屏、计数、IPC 与绘制仅作为分项定位。不能以首屏很快掩盖完整结果迟到。
- 算法或技术栈未达标时，先定位、优化或更换实现；不得通过扩大内存预算、增加可感知等待、删减排序功能来绕过要求。

热索引对标要求记录完备、索引已就绪。冷启动、首次扫描、元数据补全、重建、换页压力与后台压缩另列结果，不能与热查询混为一谈；这些阶段仍需验证界面与查询可用性。

验收要求：

1. 在该 Windows 主机上分别生成并验证 3500 万、1 亿目录项；不能在磁盘上真的创建 1 亿测试文件。生产数据只读使用，不修改现有 Everything 的数据库和配置。
2. 数据包括真实分布特征、重复名称、深层目录、长路径、中文及其他 Unicode、大小写变体、硬链接、多卷和大量同排序键记录。
3. 查询集涵盖单字符、双字符、常见和罕见子串、多条件、带空格短语、路径、无结果、全部结果及大结果集；报告每类数据，不能只给平均值。
4. 分别报告首屏、精确计数、排序切换、深分页、P50/P95/P99、取消响应、CPU、私有内存、驻留页、磁盘空间及构建峰值。
5. 使用独立的朴素实现核对样本和选定全量查询的精确计数与排序，复杂索引不自行充当正确性真值。
6. 进行百万级连续增删改名和目录移动；记录查询尾延迟、积压、追赶耗时和最终一致性。
7. 覆盖提交期间强制终止、截断或损坏索引、USN 缺口、卷离线及重连；不得要求用户手动删库才能恢复。
8. 百万级压测和长期稳定性测试在专用合成数据或隔离环境运行。不能向用户的生产磁盘注入大规模变动。
9. 合成数据验证容量与算法，3500 万生产元数据或经用户确认的代表性导出验证实际分布；两种结果分别报告。
10. 最终与同机 Everything 的相同查询和排序比较；索引配置、后台负载和冷热条件需可比。没有可比测量时不宣称达到相同性能。

## 交付顺序

### 自动发现默认流程（0.2.0）

用户明确纠正：正常使用必须自己发现并读取硬盘，不能要求输入或导入索引。默认启动已改为发现全部本地 NTFS 卷、自动恢复缓存并启动独立提权采集宿主，每卷子进程读取、保存并自动加入多卷搜索。界面移除默认演示与索引文件输入，UAC 由 Windows 处理。

缓存包含已构建排序，启动恢复执行校验而不重算排序；损坏自动回退并请求重建。卷 GUID 和挂载路径共同参与缓存身份。采集宿主跟随窗口生命周期，不借用 Everything 服务；生产服务化及实时 USN 仍属于后续范围。MFT 中不可达记录单独统计、遗漏父目录先由文件 ID 补查，不能因一条孤立记录终止整盘。

### 当前已实现阶段（0.1.0）

已交付的阶段范围是技术原型：紧凑静态索引、四列排序、查询与分页、EFU 导入、校验快照、NTFS V2 基础枚举和 WPF 界面；已在 Windows 运行 3500 万和 1 亿条合成数据测试。该结果不代表真实文件分布对标通过。

生产设计中的实时 USN 回放、服务与采集进程隔离、完整元数据与硬链接、增量可靠提交和启动自动恢复仍未实现。原型扫描不宣称形成并发文件变动下的一致性快照；需要后续按本文完整设计实现。当前首次查询主要使用全表扫描，未达到亿级即时体验目标。

1. 亿级索引布局、搜索、排序与更新的可重复基准，包含内存账本与正确性校验。
2. 通过第一阶段选型后，实现 NTFS 采集、增量持久化和故障恢复。
3. 接入 WPF 桌面、本机服务安装与可观察状态，完成 Windows 集成验收。

每个阶段是独立交付任务，分别验证与提交。第一阶段的通过只代表引擎选型获得证据，不代表完整软件已经完成。
